# Backlog — Sealed-spec enforcement & lifecycle (deferred from v8.0.0)

> Recorded by the spec-workflow-command spec (Requirement 8). These are **NOT implemented in 8.0.0** — they are the implementation-side capabilities that give the sealed spec real teeth. All consume the seal traceability written at seal time: `spec.json.sealed_spec = { run_dir, artifacts[5] }`, `phase: "sealed"`, `sealed_at`.

## Deferred items

1. **Enforcement gate (Req 8.1, 8.2).** During an implementation run, a downstream gate blocks any change not traceable to the sealed spec. May add artifact content-hashing (sha256) when built — deferred now to avoid a Windows newline-stability trap for zero present benefit.

2. **Escape hatch (Req 8.4).** An implementation run may RAISE a spec-violation finding that pauses and routes to the amendment flow (`/pipeline-orchestrator:spec --amend <run_id>`) instead of silently deviating or being hard-blocked. Keeps the contract firm but not a straitjacket.

3. **Staleness check (Req 8.5).** At implementation time, warn if the sealed spec is older than a configurable threshold OR if files it references changed since the seal, and offer re-validation.

4. **Traceability report (Req 8.6).** Map each implemented change to a sealed-spec requirement ID and flag changes with no mapping.

## Vision link

These complete the long-term goal of a unified spec→implementation pipeline: today the spec workflow stops at the seal and implementation is a separate phase; the enforcement gate + escape hatch are the seam that re-joins them under one contract.

## Status

DEFERRED — do not implement in 8.0.0. Promote to a dedicated spec when scheduled.
