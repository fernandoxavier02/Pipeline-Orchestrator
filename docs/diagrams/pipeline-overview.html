Pipeline Overview

4 phases. 26 agents. 22 gates.

From a single command to a production-ready commit, the pipeline takes your request through automatic triage, user confirmation, conditional planning, batched execution with TDD and adversarial review, and a final Go/No-Go closure.

The four phases

Each phase has a single output that becomes the input of the next. The pipeline never moves forward without a structured handoff — every transition crosses at least one gate.

Phase-by-phase

Phase 0
Automatic Triage

The task-orchestrator classifies the request: type, complexity, pipeline variant, affected files. The information-gate detects missing facts and may block. For COMPLEXA or --grill, the design-interrogator walks the decision tree before any code is touched.

SSOT_CONFLICT INFO_GATE_BLOCKED
Phase 1
Proposal & Confirmation

The pipeline presents you the classification — type, complexity, the agent team it will spawn, the gates it will enforce. You confirm, adjust, or reject. No code is touched until this gate passes.

COMPLEXITY_GATE phase-1-pipeline-proposal
Phase 2
Batched Execution with TDD & Adversarial Loop

Tasks are split into batches (1 task for COMPLEXA, 2-3 for MEDIA, all-at-once for SIMPLES). Each task goes through TDD red → implementer → spec-reviewer → quality-reviewer → checkpoint-validator → adversarial review with three independent reviewers. Findings trigger a fix loop bounded to 3 attempts.

TDD_APPROVAL CHECKPOINT_FAIL ADVERSARIAL_BLOCK FIX_LOOP_EXHAUSTED
Phase 3
Closure (Pa de Cal)

Sanity check (full build + test + regression), three independent adversarial reviewers run in parallel with zero shared context, final-validator emits Go / Conditional / No-Go with the confidence score, and finishing-branch offers four closeout options: commit, push+PR, keep, discard.

FINAL_ADVERSARIAL_GATE CLOSEOUT_CONFIRM

Complexity routing

The pipeline scales depth automatically. A typo fix does not get the same ceremony as a payment system rewrite.

Execution modes

Beyond complexity, the pipeline accepts execution mode flags that change WHICH phases run.

FULL
/pipeline-orchestrator:pipeline [task]

Default. All four phases: 0 → 1 → 1.5 → 2 → 3. Use for anything you intend to ship.

DIAGNOSTIC
/pipeline-orchestrator:pipeline diagnostic [task]

Stops after Phase 1. Classification only. Nothing is implemented. Useful for "I want to know what this task would cost".

CONTINUE
/pipeline-orchestrator:pipeline continue

Resume a paused pipeline. Triggers STALE_CONTEXT gate if context is > 24h (escalates to HARD on COMPLEXA + sensitive domain).

REVIEW-ONLY
/pipeline-orchestrator:pipeline review-only

Run only the final adversarial team on the current uncommitted dirty tree. Three reviewers in parallel, zero-context. Report only — no fixes.

HOTFIX
/pipeline-orchestrator:pipeline --hotfix [task]

Emergency bypass. Streamlined Phase 0 (BLOCKER questions only), 1 task batch, 2 adversarial checklists, minimal TDD. Reduces scope, not safety.

BRAINSTORM
/pipeline-orchestrator:brainstorm [task]

Pre-execution flow: 9 steps from intake to spec lifecycle (init / requirements / design / tasks / validate). Hands off to /pipeline or saves as standalone spec.

1 · Conserto de bug

Resolve um defeito reportado. A versão leve serve para bugs pequenos com causa óbvia; a pesada entra em ação quando o bug envolve persistência, concorrência, várias áreas do sistema ou afeta gente em produção.

LEVE Bug pequeno, causa direta — 8 passos

Usar quando o bug afeta no máximo dois arquivos, o conserto provavelmente cabe em umas cinquenta linhas e não toca em regra de negócio importante.

Exemplo concreto

O botão de "esqueci minha senha" não dispara o email. O agente entende o fluxo, escreve um teste que reproduz a falha (passo 2), descobre que falta uma variável no template (passo 3), corrige (passo 4), promove o teste a regressão permanente (passo 5), confere que o banco não foi afetado (passo 6) e pede sua aprovação no final.

Pontos onde você aprova

Dois apenas. No passo 7 o pipeline pergunta se o conserto cresceu além do esperado (em caso afirmativo, ele migra para a variante pesada). No passo 8 ele apresenta o selo final com o resumo, e você decide se manda para frente ou descarta.

PESADO Bug complexo, incidente em produção — 11 passos

Usar quando o bug envolve dados, concorrência, fluxo entre vários módulos, ou está afetando usuário em produção. Bem mais cuidadoso, com aprovação obrigatória da proposta antes de qualquer mudança.

Exemplo concreto

Pagamentos estão duplicando em horário de pico. Três agentes em sequência mapeiam o terreno, isolam a causa (corrida entre duas tarefas que gravam no banco) e descrevem o modelo de verdade do domínio. No passo 4 o pipeline trava e te mostra uma proposta de mudança controlada — você precisa aprovar antes de qualquer linha mudar. Depois, conserto mínimo, três revisores críticos independentes em paralelo, simulação da jornada do usuário, selo final, varrida final.

Pontos onde você aprova

Três pontos. No quarto passo o pipeline mostra a proposta detalhada de mudança e exige aprovação explícita antes de tocar em código. No oitavo, ele apresenta o achado dos três críticos independentes e pergunta se libera para a fase final. No décimo, o selo de Pá de Cal pede o vai/não vai definitivo.

2 · Auditoria

Examina o sistema e produz relatórios estruturados. Nunca modifica código — é só relatório. A leve e a pesada têm a mesma forma de nove passos; o que muda é a profundidade dentro de cada um.

LEVE Auditoria focada — 1 área, 1 nível de profundidade

Usar quando você quer auditar só uma parte (só a camada de dados, só o frontend, só autenticação) sem o peso de auditoria regulatória.

Exemplo concreto

Você quer entender se a parte de autenticação do sistema tem furos. O pipeline pergunta no passo 1 qual exatamente é o escopo (só login? login + recuperação de senha? só tokens?), você aprova, e ele examina sete eixos: arquitetura, domínio, contratos, dados, frontend, backend e testes. Cada eixo vira um relatório estruturado. No fim, o pipeline consolida tudo em uma matriz de risco com cada problema classificado (crítico, alto, médio, baixo) e um backlog priorizado para você ler.

Pontos onde você aprova

Dois. No passo 1, você confirma o escopo da auditoria — sem isso, ela não começa, evitando varrer o sistema inteiro sem necessidade. No passo 9, o pipeline apresenta a matriz de risco consolidada e pergunta se aceita o veredicto ou se quer que ele suba para a variante pesada (mais profundidade).

PESADO Auditoria completa — múltiplos eixos, regulatória, due diligence

Mesma sequência de nove passos da versão leve, mas cada passo é mais fundo, com agente analista de domínio dedicado nos passos 2 a 4 (em vez de checador genérico). Usar para auditoria regulatória, sistema inteiro, ou quando o relatório vai alimentar release ou due diligence.

Exemplo concreto

Auditoria regulatória completa antes de uma fusão. O pipeline coleta inventário, valida com você o escopo (todos os módulos, todos os eixos, com baseline histórico). Os passos 2 a 4 usam um agente analista de domínio dedicado, mais profundo que o checador genérico da variante leve, para mapear dependências, decisões registradas e governança de contratos. Dados, frontend e backend ganham passagem em profundidade. No fim, o selo mestre traz uma matriz de risco que cobre todos os eixos, com prioridade transversal — algo que diretoria ou advogado consegue ler.

Pontos onde você aprova

Os mesmos dois pontos da variante leve (passos 1 e 9), mas agora o passo 9 vem com a matriz de risco completa e o backlog priorizado pronto para virar plano de ação. Em ambos os pontos, o pipeline também sinaliza se algum achado é tão crítico que deveria virar um Bug Fix imediato — a remediação acontece num pipeline separado.

3 · Simulação de UX

Caminha pela jornada do usuário como se fosse um usuário real, anota onde ele trava, onde fica confuso, onde a acessibilidade falha. Também é só relatório — não modifica código. A versão leve cobre duas ou três jornadas; a pesada faz auditoria E2E completa com várias personas e dispositivos.

LEVE 2-3 jornadas, fluxo padrão — 9 passos

Usar quando você quer testar fluxos específicos ("checkout completo", "cadastro novo usuário") sem cobrir o produto inteiro.

Exemplo concreto

Você pede para o pipeline simular o fluxo de "esqueci minha senha" e o de "primeiro login depois do cadastro". O agente classifica como UX, o gate de informação pergunta quais dispositivos cobrir (web mobile? desktop?) e se acessibilidade é relevante. O simulador caminha jornada por jornada, anota cada ponto de fricção (botão difícil de achar, mensagem confusa, telinha de loading sem feedback). Você ganha um relatório estruturado com cada problema classificado.

Pontos onde você aprova

Dois obrigatórios e um opcional. No passo 3, o gate de informação pergunta dispositivos, personas e necessidades de acessibilidade se isso não estiver claro. No passo 7, ele oferece chamar três revisores críticos independentes para examinar o relatório com olhares fresh — você decide se o custo do passo extra compensa. No passo 8, o veredicto final.

PESADO Auditoria E2E completa — 5+ jornadas, cross-device, acessibilidade — 15 passos

Usar quando você quer auditoria de UX do produto inteiro, com várias personas, cobertura cross-device e acessibilidade WCAG. A versão pesada acrescenta interrogação de design no início, modo de planejamento da ordem de simulações, e revisão crítica por lote dentro da execução.

Exemplo concreto

Você pede uma auditoria de UX do app inteiro antes do relançamento. O pipeline interroga o escopo (todas as personas? incluindo daltônico e usuário de leitor de tela?), planeja a ordem das simulações (primeiro fluxos críticos como pagamento), executa uma jornada por vez com revisão crítica por lote. No final, três revisores independentes examinam o relatório consolidado e o selo de Pá de Cal traz o veredicto definitivo.

Pontos onde você aprova

Quatro pontos. Passo 3 confirma escopo e personas. Passo 4 caminha pela árvore de decisão do design (cobertura, dispositivos, critérios de severidade). Passo 9 traz a crítica por lote durante a execução. Passo 12 oferece os três revisores finais independentes. Passo 13 fecha com o veredicto. Você nunca é surpreendido.

4 · Plano (modo de planejamento)

Não é um pipeline próprio — é uma fase que entra antes da execução dentro do pipeline principal. Ela aparece automaticamente para tarefas média e complexa, e pode ser pedida com a flag de plano nas tarefas simples. O agente entra em modo só-leitura, examina o código, devolve um plano estruturado, você aprova antes de qualquer linha mudar.

Exemplo concreto

Você pede para adicionar autenticação social ao app. O pipeline classifica como complexa (auth eleva automaticamente), entra em modo plano sem tocar em código. O arquiteto examina como autenticação atual funciona, mapeia padrões existentes, e devolve um plano: "vai criar três arquivos novos, modificar dois existentes, na ordem A → B → C, riscos principais são X e Y, leva ~6 lotes". Você lê, ajusta ou aprova. Só então a execução começa.

Pontos onde você aprova

Um ponto, mas dos mais importantes. Você aprova o plano completo antes de qualquer arquivo ser tocado. Pode rejeitar, pedir refazer, ou ajustar pontos específicos. Para tarefa simples, o modo plano é pulado por padrão (passe a flag de plano para forçar). Em complexa, é obrigatório.

5 · Brainstorm (preparação antes do pipeline)

Roda antes do pipeline de execução, para tarefas onde ainda falta esclarecer o que você quer. Faz captura inicial, exploração dinâmica de perguntas (até onze dimensões de gaps), proposta de abordagens alternativas, e produz uma especificação completa (requisitos, design, tarefas) pronta para virar pipeline.

Exemplo concreto

Você fala "quero adicionar relatórios financeiros mensais" e nada mais. O passo 2 é o coração da preparação: o agente lê o projeto, identifica que faltam decisões críticas (formato de exportação? quais métricas? quem aprova? cobertura tributária?) e te pergunta uma a uma com evidência de onde no código a ambiguidade está. O passo 3 oferece quatro caminhos (do mínimo viável ao agressivo). Daí ele constrói requisitos formais, valida contra o que já existe, propõe um design, valida, e quebra em tarefas. No fim, você decide: vira pipeline agora ou guarda a spec para depois.

Pontos onde você aprova

Três pontos principais. Passo 2 é dinâmico — pode haver uma ou várias perguntas, dependendo de quantos gaps reais o agente encontra no seu pedido. Passo 3 é onde você escolhe a abordagem entre as alternativas propostas. Passo 8 valida que o design proposto cobre todos os requisitos antes de quebrar em tarefas. No fim, você decide se entrega para o pipeline ou se guarda só a spec.

6 · Hotfix (emergência)

Modo de emergência. Reduz escopo, não segurança. Roda só as perguntas absolutamente críticas no início, lote único, duas listas de verificação adversariais em vez de sete, sanidade mínima, fechamento expedito. Usar quando o sistema está parado e você precisa subir um conserto agora.

Exemplo concreto

Login parou em produção. O hotfix entra com triagem ultra-rápida: só pergunta "qual é o erro no log? quando começou? quem está afetado?". Você confirma o escopo mínimo (vamos consertar só o problema imediato, refinamento fica para depois). Lote único: teste, conserto, build. Duas listas adversariais — autenticação e injeção, que são as áreas onde um conserto rápido costuma criar buraco novo. Sanidade só de build, sem rodar suite completa. Veredicto e sobe.

Pontos onde você aprova

Três pontos compactados. Triagem só com perguntas críticas (sem o gate longo de informação). Confirmação do escopo mínimo. Veredicto final expedito. Importante: o hotfix corta ceremônia, não corta segurança — a crítica adversarial ainda roda, só foca em auth e injeção. Depois que o conserto sobe, o ideal é abrir um follow-up para passar pelo pipeline completo.

7 · Revisão isolada (review-only)

Roda só a equipe de revisão crítica final contra o código que você já escreveu (a árvore atual, mesmo com mudanças não salvas). Três revisores em paralelo, sem contexto compartilhado, devolvem o que acharam. Só relatório — nada é consertado automaticamente, nada é commitado.

Exemplo concreto

Você escreveu um conserto sozinho e quer uma segunda opinião antes de abrir pull request. Pede revisão isolada. O pipeline mostra o custo estimado (porque chamar três revisores cheios gasta tokens), você autoriza. Os três rodam em paralelo, cada um sem ver o que os outros encontraram, examinando o mesmo código com olhares diferentes. Você recebe um relatório consolidado com cada achado classificado por severidade. Nada é consertado, nada é commitado — você decide o que fazer.

Pontos onde você aprova

Um ponto só. A autorização de rodar a equipe de três revisores, porque tem custo de tokens não trivial. Depois disso, o pipeline trabalha sozinho até entregar o relatório. Importante: esse modo é só leitura — não dá para corrigir automaticamente dentro dele. Se você quer aplicar correções, abre um novo pipeline (bugfix ou pipeline completo) com os achados como input.
