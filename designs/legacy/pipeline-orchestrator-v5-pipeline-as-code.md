## Problem Statement

O plugin `pipeline-orchestrator` (v4.1.0 atual) é tecnicamente sólido — 38 agentes em camadas, hooks de guard, Sentinel, classificação automática, gates de qualidade. Mas é uma caixa-preta opaca pra quem usa. Cinco sintomas catalogados:

1. **Mono-skill condensada** — único entry point (`/pipeline-orchestrator:pipeline`), esconde diversidade de comportamentos atrás de classificação implícita.
2. **Classificador opaco** — `task-orchestrator` decide tipo+complexidade sem trilha de raciocínio visível.
3. **Falta de observabilidade live** — durante execução não há visualização de fase em curso, gates passados/falhados.
4. **Ausência de slash commands específicos** — não é possível forçar `bugfix`, `feature`, `audit`, `ux` diretamente.
5. **Auditoria do auditor inexistente** — não há mecanismo que confirme que cada pipeline interno ainda segue as boas práticas que promete (ex: pipeline de Feature ainda inclui design antes de implementação).

Os cinco têm a mesma raiz: **opacidade arquitetural**.

## What Makes This Cool

A versão sensacional do plugin não é "mais agentes". É a inversão filosófica: pipeline-orchestrator vira o primeiro plugin Claude Code construído como **caixa de vidro por design**.

Três propriedades que nenhum plugin Claude Code entrega bem hoje:

- **Pipeline declarativo, versionado, lido pelo usuário antes de rodar.**
- **Trilha de auditoria persistida em git, anexável a PR.**
- **Auditoria do auditor via golden runs — testes que validam que cada pipeline ainda faz o que promete.**

Posicionamento defensável porque é estrutural, não cosmético. Outros plugins podem adicionar logs ou diagramas — só esse teria a fundação desenhada pra ser explicável e auditável. Tipo de coisa que vira referência arquitetural na comunidade.

## Constraints

- Plugin pessoal, OSS, MIT, FX Studio AI; sem time grande.
- Pré-1.0 mainstream — janela de breaking changes ainda gerenciável.
- Stack: Markdown com YAML frontmatter pra agentes/skills, JS CommonJS pra hooks, Claude Code 2.x.
- Compatibilidade obrigatória: `/pipeline-orchestrator:pipeline` precisa continuar funcionando idêntico em v5.
- Persona alvo: arquiteto B2B senior. Previsibilidade > magia, trilha persistida > visualização animada, conformidade > experiência ágil, controle explícito > defaults inteligentes.
- Janela de implementação realista: dono é solo, paga por sprints curtos. Boil the lake é viável; boil the ocean não é.

## Premises

Cinco premissas validadas em sessão de office-hours em 2026-04-26:

1. Persona alvo é arquiteto B2B senior; previsibilidade, auditoria persistida, conformidade e controle explícito ranqueiam acima de magia, animação, agilidade e defaults.
2. Tema unificador é caixa de vidro: explicável, navegável, auditável por design.
3. Arquitetura consolida no nível plugin (um plugin cobre audit, feature, bugfix, UX) e modulariza no nível skill+slash command.
4. "Aprendizado das execuções passadas" é documentação acumulada e consultável (artefato somente-leitura), não aprendizado adaptativo do classificador. Determinismo preservado.
5. Os cinco problemas têm raiz comum (opacidade) e devem ser resolvidos por redesign coerente, não por cinco fixes desconectados.

## Approaches Considered

### Approach A — Pipeline Trace (mínimo viável)

Slash commands explícitos por tipo + TRACE.md por execução, mantendo arquitetura interna como está. Esforço S–M, risco baixo, cobre 3 dos 5 problemas. Não resolve mono-skill nem opacidade durante execução.

### Approach B — Pipeline as Code (recomendada)

Refatoração estrutural: cada tipo vira sua própria skill+command, definição declarativa em YAML, golden runs como auditoria do auditor, TRACE.md persistido. Esforço L, risco M, cobre os 5 problemas com escopo honesto e fases.

### Approach C — Pipeline Inspector (lateral)

`/inspect` e `/explain` em cima da arquitetura atual, foco em explicabilidade UX. Esforço M, risco baixo–médio. Solução parcial — não resolve mono-skill nem auditoria do auditor sozinha.

## Recommended Approach

**B — Pipeline as Code, fasada em três marcos (v5.0, v5.1, v5.2), com C absorvido em v5.1.**

A revisão adversarial mostrou que tentar entregar B+C+golden runs num único v5.0 é boil the ocean, não boil the lake. Reorganização honesta:

- **v5.0** — multi-skill + multi-command + TRACE.md + YAML declarativo + compat regression suite. **Núcleo do redesign.**
- **v5.1** — golden runs (auditoria do auditor) + parte do Inspector (`/explain` sobre TRACE passado).
- **v5.2** — Inspector completo (`/inspect` pré-execução com diagrama ASCII).

Esta seção descreve v5.0. v5.1 e v5.2 ficam como contratos futuros, não compromissos de release agora.

### Pré-requisitos (bloqueiam implementação)

Estes precisam estar fechados antes de qualquer linha de código.

**P-1. Schema YAML congelado.** Documento curto (uma página) em `references/pipelines/SCHEMA.md` cobrindo:

- Estrutura de fase (`id`, `purpose`, `agents`, `inputs`, `artifacts`).
- Mapeamento dos 15 gates existentes do v4 (`SSOT_CONFLICT`, `ADVERSARIAL_GATE_MANDATORY`, `INFO_GATE_BLOCKED`, `TDD_APPROVAL`, `PLAN_REJECTED`, `MICRO_GATE_GAP`, `CHECKPOINT_FAIL`, `ADVERSARIAL_BLOCK`, `FINAL_ADVERSARIAL_REWORK`, `STOP_RULE`, `FIX_LOOP_EXHAUSTED`, `STALE_CONTEXT`, `ADVERSARIAL_GATE`, `FINAL_ADVERSARIAL_GATE`, `CLOSEOUT_CONFIRM`) em construtos YAML — qual fica em `gates_before`, qual em `gates_during`, qual em `gates_after`, qual é cross-cutting.
- Como `complexity` (`SIMPLES`, `MEDIA`, `COMPLEXA`) é representada — `complexity_branches` interno a um único YAML, com fases condicionais, em vez de múltiplos arquivos. **Fundir `bugfix-light` + `bugfix-heavy` em `bugfix.yaml`**, mesmo padrão pros outros tipos.
- Como modos (`--hotfix`, `continue`, `review-only`, `--grill`, `--plan`, `--simples`, `--media`, `--complexa`) são representados — flags ortogonais ao tipo, processadas pelo controller antes de carregar YAML.
- Schema versioning: cada YAML tem `schema_version: 1`. Loader rejeita versão desconhecida.
- Security: allow-list de phase ids, agent names, gate names. YAML que tenta inserir agent ou gate desconhecido é rejeitado pelo loader.

**P-2. Compat regression suite.** Antes de tocar no `commands/pipeline.md` (~1100 linhas) ou nos 7 hooks, congelar o comportamento da v4.1.0 em testes que validam que `/pipeline-orchestrator:pipeline` produz exatamente os mesmos artefatos e logs em N cenários canônicos. Sem isso, qualquer divergência sutil quebra retrocompat sem aviso.

**P-3. Spike de formato (30 minutos).** Comparar YAML, Markdown com frontmatter, e JSON pra um pipeline simples (`bugfix`). Decidir e documentar. Inclinação por YAML, mas não bater martelo sem ver os três.

### Componentes do v5.0

**C-1. Refactor multi-command + multi-skill.**

Mecanismo correto em Claude Code 2.x: skills são auto-discovered por descrição, *commands* têm slash invocation explícita via arquivo em `commands/`. Pra ter `/pipeline-orchestrator:bugfix [task]` é preciso criar `commands/bugfix.md`. As skills são auxiliares de auto-discovery, não bind de slash command.

Estrutura proposta:

```
commands/
├── pipeline.md     (auto-classifier, atual; mantido)
├── bugfix.md       (NOVO: força tipo=bugfix)
├── feature.md      (NOVO: força tipo=feature)
├── audit.md        (NOVO: força tipo=audit)
└── ux.md           (NOVO: força tipo=ux)

skills/
├── pipeline/SKILL.md       (atual; thin, delega ao controller)
├── bugfix/SKILL.md         (NOVO; thin, delega com tipo fixo)
├── feature/SKILL.md        (NOVO)
├── audit/SKILL.md          (NOVO)
└── ux/SKILL.md             (NOVO)
```

Cada novo command faz Agent dispatch ao `pipeline-controller` agent passando `pipeline_type` fixo. O controller pula classificação e vai direto pra carregar o YAML correspondente.

Modos (`--hotfix`, etc.) ficam ortogonais a tipo: `/pipeline-orchestrator:bugfix --hotfix [task]` é válido. Matriz `commands × modes` documentada formalmente em `docs/commands-modes-matrix.md`.

**C-2. Pipeline-as-YAML (interpretado pelo controller).**

Cada pipeline é descrito declarativamente em `references/pipelines/{tipo}.yaml`. Exemplo (esboço, schema final em P-1):

```yaml
schema_version: 1
name: bugfix
description: Bug fix pipeline with diagnostic, root-cause analysis, fix, regression test

complexity_branches:
  SIMPLES:
    phases: [diagnostic, implementation, verification]
  MEDIA:
    phases: [diagnostic, root-cause, implementation, verification]
  COMPLEXA:
    phases: [diagnostic, root-cause, implementation, verification, adversarial]

phases:
  diagnostic:
    purpose: Reconnaissance and ranked hypothesis
    agents: [bugfix-diagnostic-agent]
    gates_before: [INFO_GATE_BLOCKED]
    artifacts: [DIAGNOSTIC_REPORT]

  root-cause:
    purpose: Confirm root cause with evidence chain
    agents: [bugfix-root-cause-analyzer]
    inputs: [DIAGNOSTIC_REPORT]
    artifacts: [ROOT_CAUSE_RESULT]

  implementation:
    purpose: Apply minimal fix
    agents: [executor-implementer-task]
    inputs: [ROOT_CAUSE_RESULT]
    gates_during: [TDD_APPROVAL]

  verification:
    purpose: Regression and adjacent-breakage check
    agents: [bugfix-regression-tester]
    gates_after: [CHECKPOINT_FAIL, FINAL_ADVERSARIAL_GATE]

  adversarial:
    purpose: Adversarial review on COMPLEXA tasks only
    agents: [adversarial-review-coordinator]
    gates_after: [ADVERSARIAL_GATE_MANDATORY]

success_criteria:
  - root_cause_documented
  - regression_tests_pass
  - sanity_check_passed
```

O `pipeline-controller` (em `agents/core/pipeline-controller.md` — agent, não command) refatora pra: ler argumentos (`pipeline_type`, `mode`, `complexity_override`), carregar YAML correspondente, executar fases na ordem, aplicar gates conforme schema. Toda lógica de fase/gate sai de inline pra dirigida por dados.

**C-3. Refactor dos 7 hooks pra pipeline-aware.**

Cada hook em `.claude/hooks/` precisa ser auditado e potencialmente reescrito:

- `force-pipeline-agents.cjs` — reconhecer todos os 5 padrões de comando (`pipeline`, `bugfix`, `feature`, `audit`, `ux`).
- `session-lock-hook.cjs` — entender que tipo de pipeline está locked (campo novo no `sentinel-state.json`).
- `sentinel-hook.cjs` — calcular `expected_next` lendo o YAML carregado em runtime, não de tabela hardcoded.
- `dispatch-guard.cjs` — validar dispatches contra a lista de agents permitidos pelo YAML do pipeline em curso.
- `edit-guard-hook.cjs` — sem mudança esperada, mas auditar.
- `completion-checklist.cjs` — sem mudança esperada, auditar.
- `session-cleanup-hook.cjs` — sem mudança esperada, auditar.

Documento em `docs/hooks-v5-changes.md` lista por hook: o que muda, o que não muda, quem testa.

**C-4. TRACE.md (Run Record) persistido.**

Renomeado de "ADR de execução" pra "Run Record" — ADR é convenção pra decisões arquiteturais (Nygard 2011), não logs de execução. Confunde leitor.

Localização: `.pipeline-orchestrator/runs/{YYYYMMDD-HHMMSS}-{6char-random}-{slug}/TRACE.md`. Sufixo aleatório evita colisão entre worktrees ou usuários simultâneos. Diretório versionado no repo do usuário por padrão (auditável, anexável a PR), com `.gitignore` opcional documentado.

Schema do TRACE.md tipado:

```markdown
# Pipeline Run: {slug}

- trace_schema_version: 1                       # int
- timestamp_utc: 2026-04-26T15:30:00Z          # ISO 8601 UTC
- started_at: 2026-04-26T15:30:00Z             # ISO 8601 UTC
- ended_at: 2026-04-26T15:42:31Z               # ISO 8601 UTC
- duration_seconds: 751                         # int
- plugin_version: 5.0.0                         # semver
- user_identity: fernandoxavier02@github       # fonte: git config user.email se em repo, OS user fallback
- branch: feature/v5-rc1                       # git branch atual ou "(no-git)"
- repo: github.com/fernandoxavier02/Pipeline-Orchestrator   # git remote ou "(local)"
- task: {task description provided by user}

## Classification
- type: bugfix
- type_source: manual via /pipeline-orchestrator:bugfix    # OR auto via /pipeline
- complexity: COMPLEXA
- complexity_source: auto (rationale: domains_touched=3)
- justification: {prose, 2-3 sentences}

## Pipeline Definition (snapshot)
{cópia integral do YAML carregado, garante reprodutibilidade mesmo se YAML mudar depois}

## Execution Log
### Phase: diagnostic
- started_at: 2026-04-26T15:30:00Z
- ended_at: 2026-04-26T15:32:14Z
- agents: [bugfix-diagnostic-agent]
- gate_before: INFO_GATE_BLOCKED → PASS
- artifacts_produced: [DIAGNOSTIC_REPORT]
- status: SUCCESS

### Phase: root-cause
... (idem)

## Final Verdict
- status: SUCCESS | DONE_WITH_CONCERNS | BLOCKED
- artifacts: [list of files modified, tests added]
- open_issues: [...]
- recommended_next: {prose}
```

Versionamento: `trace_schema_version` permite que TRACE.md gerados em v5 sejam lidos por v5.1+, e que tooling externo (futuros parsers, dashboards) versione contra schema fixo. Política de retenção: TRACEs ficam indefinidos (são pequenos, são versionados em git); usuário decide com `.gitignore` ou cleanup manual. v5.0 não implementa rotation.

**C-5. Compat regression suite (do P-2, mas é também entregável).**

Sob `tests/compat/v4-baseline/`, N cenários canônicos do v4.1.0 com snapshots de comportamento. Roda como CI step antes de qualquer merge. Se algum snapshot diverge, build falha e PR não merge sem revisão explícita. Esse é o contrato que sustenta a promessa de "100% retrocompatível em `/pipeline-orchestrator:pipeline`".

**C-6. Histórico consultável (Premissa #4).**

`pipeline-controller` ganha capacidade opcional de carregar TRACE.md de runs passados como referência somente-leitura no contexto. Implementação mínima em v5.0: comando `/pipeline-orchestrator:audit` ganha flag `--use-history`, que faz o controller carregar até 5 TRACEs mais recentes do mesmo tipo no diretório `.pipeline-orchestrator/runs/` e injetá-los como contexto somente-leitura no prompt do agent. Sem aprendizado adaptativo, sem mudança de classificador. Determinismo preservado.

## Open Questions

1. **`/pipeline` continua entry point principal ou passa a fallback?** Inclinação: fallback documentado, com mensagem amigável de descoberta dos commands específicos. Trava: documentação de README precisa ser bem feita pra não afastar usuário casual.

2. **Modos (`--hotfix`, etc.) são preservados em todos os 5 commands?** Inclinação: sim, todos preservados, mas alguns podem não fazer sentido em todos os tipos (ex: `--grill` em `audit` é redundante). Matriz commands × modes responde isso formalmente em P-1.

3. **YAML loader rejeita YAML com agent ou gate desconhecido (estrito) ou ignora com warning (permissivo)?** Inclinação: estrito por default, com flag `--allow-unknown` pra desenvolvimento local.

4. **TRACE.md vai pro repo do usuário (versionado) ou pra `~/.claude/data/...` (privado)?** Inclinação: repo do usuário por default, com config `pipeline-orchestrator.runs_location` em `.claude/settings.json` permitindo override pra `~/.claude/data/pipeline-orchestrator/runs/`.

5. **Como TRACE.md gerados em v5.0 se comportam quando o usuário faz downgrade pra v4.1.0?** v4 não conhece esse formato. Inclinação: v4.1 fica indiferente (TRACEs são apenas markdown em diretório que v4 ignora). Documentar isso explicitamente no migration guide.

## Success Criteria

Critérios técnicos verificáveis (todos obrigatórios pra release v5.0):

- Cinco commands funcionais em `commands/`: `pipeline`, `bugfix`, `feature`, `audit`, `ux`.
- Cinco skills em `skills/` correspondentes (thin, auto-discoverable).
- `references/pipelines/*.yaml` define os 4 tipos declarativamente; `pipeline-controller` interpreta o YAML em vez de ramos hardcoded.
- `tests/compat/v4-baseline/` passa em CI; nenhum cenário canônico do v4.1.0 produz divergência inesperada de comportamento.
- Cada execução gera Run Record (`TRACE.md`) em formato `trace_schema_version: 1`.
- README v5 atualizado com matriz commands × modes e migration guide v4→v5.
- CHANGELOG entry detalhado.
- `/pipeline-orchestrator:pipeline` continua passando nos testes existentes do v4.

Outcome metrics (não-bloqueantes pra release, observados após):

- Pelo menos um teste real em projeto próprio do dono (rodar `audit` em repo real, gerar TRACE, anexar a PR fictício, validar plausibilidade).
- Pelo menos uma menção do plugin (post, comentário, fork) por alguém da comunidade Claude Code referenciando "caixa de vidro" — sinal externo de pega.

## Security Model

YAML loader é nova superfície de ataque. Se atacante corrompe `references/pipelines/feature.yaml`, ele muda o fluxo de execução do pipeline.

Mitigações em v5.0:

- **Allow-list de phase ids, agent names, gate names** — loader rejeita qualquer valor fora do conjunto registrado.
- **Schema validation** com `schema_version` checagem antes de qualquer interpretação.
- **YAML loader em modo seguro** (sem `!!python/object` ou tags equivalentes).
- **Anti-injection invariant atualizado**: `references/pipelines/*.yaml` continuam sendo DATA, não authoritative — controller interpreta, não executa código embutido. Documentado em `commands/pipeline.md`.
- **PR review obrigatório em mudanças de `references/pipelines/`** via CODEOWNERS no GitHub.

Threat model formal em `docs/security-model-v5.md`.
